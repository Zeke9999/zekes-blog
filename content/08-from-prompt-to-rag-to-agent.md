最近重新整理一份Stanford CS230 | Autumn 2025 | Lecture 8: Agents, Prompts, and RAG的笔记。

如果只把这些词拆开来看，很容易变成一堆流行术语；但把它们放回同一条问题链里，逻辑其实很清楚：**模型已经足够强，但距离“稳定可用的系统”还有几步。** 下面几部分，基本就是我对这条主线的重新展开。文末最后一节也顺手放了两点我当时写在纸边上的题外话，那不是课程原话，而是我自己的判断。

## 基础模型已经很强，但问题并没有消失

课程开头先谈的不是技巧，而是边界。通用大模型当然已经很强了，但真到了落地阶段，几个老问题还是会反复出现：它未必懂你的行业，不一定知道最新信息，偶尔会一本正经地胡说，模型本身还可能过重、过贵、过慢，而且输出行为也很难像传统程序那样被精确约束。

这几个问题放在一起看，会得出一个很现实的结论：**模型能力不等于系统能力。** 一个模型能把一句话续写得很好，不代表它已经能承担业务里的知识查询、流程执行、格式约束、结果校验和错误回退。很多团队做 LLM 应用，一开始卡住也往往不是因为模型“太弱”，而是因为直接把模型当系统来用了。

所以后面不管是 Prompt、Fine-tuning 还是 RAG，本质上都是在回答同一个问题：怎样把一个很强但不稳定的基础能力，变成一个更接近真实生产环境的系统部件。

## Prompt 当然重要，但它解决不了全部问题

这几年 Prompt Engineering 被反复强调，不是没有原因。很多任务里，提示词确实是成本最低、见效最快的优化入口。任务边界讲清楚、输出格式定清楚、约束条件写清楚，结果往往立刻就会好很多。

但教授也明确提出，提示词工程更应该是每个人都应该掌握的技能，而不是一个好的career选择。确实如此，2023年呼声很高的提示词工程是，让很多人以为文科生也能进AI大厂拿高薪了，但是呼声退去之后，2026年的现在prompt engineer出现的频率越来越少了。

原因很简单。Prompt 主要解决的是“如何更好地驱动模型”，但它并不能凭空给模型补上最新知识，也不能直接提供外部工具能力，更不能替你管理一个长流程里的状态、重试、分支和评估。很多人早期做 LLM 应用时，会下意识把所有问题都堆回 prompt 里，最后 prompt 越写越长，系统却没有变得更稳。

真正有经验以后我意识到，Prompt 更像是第一层控制面：先把任务说清楚，再决定哪些问题应该交给检索、哪些问题应该交给工作流、哪些问题压根不该继续让模型自由发挥。这些内容都是要长期和一个模型打交道，慢慢总结出来的。可惜的是，LLM的基座模型发展太迅速，对提示词的宽容度越来越好，能够基于一般（口头的）prompt，生成过得去的output，也许只有训练模型的机构能够彻底了解模型的特性，组织最好的prompt，完全榨取LLM的所有能力。

## Zero-shot、Few-shot 和 Prompt Chaining，本质上都在降低任务歧义

Zero-shot 是不给例子，直接让模型做事；Few-shot 是给少量样例，让模型沿着样例去模仿。真正有用的地方在于：**示例经常比抽象描述更有效。** 你写一大段“请保持语气克制、结构清晰、不要空话”，很多时候还不如直接给模型两段你想要的输出样子。

使用样例很重要，因为大模型的Transformer架构很适合延续已知的、确定性的、固定流程的内容，所以学习示例的能力和模仿示例的能力都很强。

还有一部分是 Prompt Chaining。它的思路也不复杂：既然一个问题太大、太杂，那就别让模型一次做完，而是拆成几个更容易控制的子步骤。先抽取信息，再归纳，再判断，最后生成。这样做最大的价值，不只是效果可能更稳定，而是**你终于能看见错误出在哪一步**。但是应该注意的是，使用Prompt Chaining会占用更多的上下文空间，以及降低输出的效率。

## Fine-tuning 教授个人不喜欢微调

微调这件事，课程里讲得很克制。它当然有用，但代价也很真实：贵、慢、需要高质量数据，而且不是随便收集一点样本就能做出稳定收益。

如果问题只是“模型不知道最新资料”，那微调通常不是优先选项。因为这类问题更适合用外部知识去补，而不是把新知识重新烤进参数里。参数更新慢、成本高，而且知识一变又要重新来一次，这条路对多数团队都不划算。

微调更适合解决的，是另一类问题：你希望模型长期稳定地呈现某种能力分布。比如某种固定文风、某类垂直术语体系、某种结构化输出习惯，或者某种特定语言和表达能力。如果任务规模足够大、样本足够稳定、调用频率足够高，微调的投入才可能开始变得值得。

所以在实际工程里，更常见的顺序往往不是“先微调”，而是先把 Prompt、检索、工作流和评估做扎实，再看还有没有必要把其中一部分能力内化进模型。

## RAG 几乎成了企业落地的默认配置，不是偶然

为什么大家都在做 RAG？因为工程中实际使用AI时，会面临各种问题：模型知识不够全，信息不够新，回答容易脱离真实资料，企业内部数据又不可能直接靠预训练解决，如果完全依赖LLM底座，它甚至不知道今天是什么天气（因为知识更新截止到训练阶段）

RAG 的思路并不复杂：先检索，再生成。先把和当前问题最相关的外部信息找出来，再让模型基于这些材料回答。它最直接的收益通常有四个：补知识、降幻觉、处理信息更新，以及接入内部数据。

这也是为什么 RAG 对企业尤其重要。很多业务里真正关键的并不是“模型懂不懂世界”，而是“它能不能准确使用我的资料”。产品文档、制度规范、项目沉淀、知识库、会议记录、内部 SOP，这些内容才决定系统在具体组织里有没有用。

向量数据库在这里承担检索功能，它只是帮助系统把文档切片、建立索引、附带元数据，并在查询时尽快找到最相关的那几段。真正决定体验的，往往反而不是“有没有上向量库”，而是文档怎么切、召回准不准、上下文怎么组织、长文档是按什么粒度进入模型。

这一点在 long document 场景里尤其明显。长文档不是一股脑塞进上下文就完了，而是要按章节、语义段落或者结构单元切开，需要时再按问题把相关片段取出来。换句话说，RAG 的核心不是“让模型读更多”，而是“让模型只读当前最该读的那部分”。有些类似于存储管理中的三层分页查找的过程。

## 真正把系统往前推一步的，往往是 Workflow 和 Agent

前面几层解决的，大多还是“模型知道什么、怎么回答”的问题；到了 Workflow 和 Agent，关注点就变成了“系统怎么做事”。

这也是很多人真正开始进入工程区之后，感受最明显的一道分水岭。聊天式问答当然很直观，但真实业务通常不是一句话问完就结束。一个请求进来，系统可能要先判断类型，再决定是否检索，再去调工具，再读结果，再做下一步判断，最后还要输出一个可用、可审计、可回放的结果。

这时候，Workflow 的价值就出来了。它把可预定义的步骤先固定下来，让系统按稳定路径走；而 Agent 的价值，则在于当路径没法提前完全写死时，系统还能根据中间观察结果继续决策。两者不是互斥关系，更多时候反而是叠加关系：**能固定的地方尽量固定，必须动态决策的地方再交给 Agent。**

从这个角度看，Agent 不是“一个更会聊天的模型”，而是一套围绕目标推进任务的执行结构。它真正补上的，是检索、工具调用、状态推进、错误恢复和路径调整这一整层能力。

## 做案例时，最重要的问题其实不是“能不能做”，而是“怎么知道它真的有效”

那么应该怎么做一个Agent或者Workflow呢？首先拆业务流程，再设计 Agent 和 Workflow，最后别忘了问一句——**How would you know if it works?**

让模型跑出一个看起来不错的 demo 并不难，真正难的是定义什么叫成功，什么叫失败，什么提升值得要，什么问题必须拦住。

如果没有评估，系统很容易陷入一种错觉：看上去很聪明，实际上不稳定；偶尔特别惊艳，但大多数时候不可靠。尤其是 Agent 任务，最后成败不只是模型生成得好不好，还包括检索有没有找对、工具有没有调通、流程有没有中断、重试是不是有效。

所以真正靠谱的做法，通常都要回到一个很土但很有效的过程：先拆任务，再搭流程，再定义评估。很多工程决策最终都不是靠感觉做出来的，而是靠一轮轮测试和回放把边界磨清楚。

这也就显示出来Agent的评估和benchmark的重要性。

## 自言自语

第一点和 Prompt Engineering 有关。我的直觉是，Prompt 在相当长一段时间里仍然重要，但它更像一项基础能力，而未必会长期作为一个边界清晰、壁垒稳定的独立职业存在。随着模型能力继续增强、系统模板逐渐固化、自动化优化手段越来越多，很多原本靠人工反复雕 prompt 的工作，迟早会被吸收到更上层的工程流程里。

第二点和职业判断有关。AI 发展越快，越要警惕那些被包装得很新、听起来很高级、但底层其实高度依赖模型红利的岗位。短期看，市场总会制造一批新名词；但拉长来看，更稳的能力通常还是那些不容易被替代的东西：理解模型边界、理解业务流程、能做系统设计、能接工具、能做评估。这些能力就算换一轮技术浪潮，价值也更容易留下来。

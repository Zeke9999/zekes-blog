在多数工程场景中，优先设计 Workflow 往往比直接构建 Agent 更重要。原因不在于 Agent 缺乏能力，而在于系统首先需要可预测性、可验证性和可维护性。只有当任务路径难以预先枚举，且确实需要模型在运行中持续做决策时，Agent 带来的额外复杂度才值得引入。

## Agent 和 Workflow 的区别，本质上是架构重心不同

Anthropic 在 *Building Effective Agents* 中将两者区分为两类架构：
- Workflow：LLM 和工具沿着预定义代码路径被编排执行
- Agent：LLM 在执行过程中动态决定流程与工具使用方式

因此，更准确的理解方式是：**Workflow 更偏确定性编排，Agent 更偏动态决策。**

这种差异直接带来一组工程权衡：
- 成本更高
- 耗时更长
- token 消耗更多
- 行为更难预测
- 调试复杂度更高

真正需要回答的问题不是“能不能做 Agent”，而是：**当前问题是否真的需要 Agent。**

## 什么时候优先用 Workflow

如果一个任务满足下面几个特征，通常更适合先做 Workflow：
- 步骤比较清楚
- 输入输出边界明确
- 中间环节可预定义
- 成功标准相对稳定

典型例子包括：
- 信息抽取
- 固定格式改写
- 分类与路由
- 文本生成后的格式检查
- 标准化数据处理

这类任务最需要的是稳定性，而不是额外的“自主性”。在这类场景中，把流程拆成若干可验证步骤，通常比让模型自由决定路径更容易获得稳定结果。

## 什么时候才考虑 Agent

只有当任务具备下面这些特点时，Agent 才真正有价值：
- 目标明确，但路径不固定
- 执行过程中要不断与环境交互
- 需要搜索、修正并继续尝试
- 需要根据观察结果动态改变策略

例如：
- 自动排查复杂问题
- 在多个工具之间来回协作完成任务
- 长链路的软件工程问题处理
- 开放式信息探索与归纳

这类任务往往无法提前写出完整路径。此时，Workflow 会逐渐变得僵硬，而 Agent 的动态决策能力才开始体现优势。

## 先做简单系统，通常是更稳妥的工程策略

一个常见误区，是为了追求“更像 Agent”而过早引入复杂自治能力。

更合理的工程路径通常是：
1. 先把稳定部分抽成 Workflow
2. 把可枚举的路径做成 Routing
3. 只有在固定流程覆盖不了的环节，再引入 Agent

这背后的原则很直接：**能确定的事情，不要无条件交给模型自由发挥。** Anthropic 也明确建议，构建 LLM 应用时应先寻找“足够简单且可用”的方案，只有在复杂度确实带来收益时再增加系统复杂度。

## Workflow 不是过渡方案，而是长期基础设施

成熟系统通常不是“全面 Agent 化”，而是把不同机制放在合适的位置：
- Workflow 负责稳定与约束
- Agent 负责开放任务中的弹性与探索

很多看起来像 Agent 的系统，底层仍由多个 Workflow 组织起来，只是在关键节点把“下一步如何做”的决策权交给模型。因此，Workflow 并不是 Agent 出现之前的临时方案，而是 Agent 时代依然重要的基础设施。

## 一个实用判断标准

在方案评估时，可以先问三个问题：
- 这个任务的步骤能不能明确写出来？
- 这个任务的成功标准能不能清楚验证？
- 这个任务是否真的需要动态决策？

如果前两个问题的答案是“能”，第三个问题的答案是“不一定”，通常应优先从 Workflow 开始。

## 结语

在工程实践中，**稳定、可观测、可验证** 往往比“看起来更智能”更重要。一个成熟的 AI 系统，不是尽可能把所有问题都包装成 Agent，而是在该稳定的地方使用 Workflow，在该灵活的地方引入 Agent。

这也是为什么，Workflow 往往不是 Agent 的过渡形态，而是 Agent 系统长期存在的底层结构。

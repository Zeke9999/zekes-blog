## 五种基本的 Multi-Agent
- 生成验证者（Generator - Verifier）
- 调度者-子智能体（Orchestrator）
- 智能体团队（Agent Team）
- 消息总线（Message Bus）
- 共享状态（Shared State）

很多人一提到 Multi-Agent，第一反应是“让多个 Agent 一起工作，效果会不会更强”。但从工程视角看，Multi-Agent 真正处理的从来不是“数量问题”，而是**复杂度管理问题**。由于context的限制，单个 Agent 面对困难的任务时，已经难以同时承担规划、执行、检索、校验、汇总这些职责，系统必须开始回答几个更具体的问题：

- 任务应该怎么拆？
- 不同角色如何分工？
- 信息通过什么方式传递？
- 多个 Agent 如何避免重复劳动？
- 中间状态是靠消息传递，还是靠共享存储维护？

这里汇总了五种基本的 Multi-Agent 结构，本质上就是对这几个问题的五种不同回答。

## Multi-Agent 不是默认答案，而是复杂任务下的结构选择

并不是所有任务都值得引入 Multi-Agent。

如果一个问题本身路径清晰、上下文不大、成功标准也容易验证，那么单 Agent 往往更便宜、更直接，也更容易调试。只有当下面这些信号开始同时出现时，多智能体结构才真正有意义：

- 单个 Agent 的上下文容量开始成为瓶颈
- 任务可以自然拆成若干子问题
- 不同阶段需要明显不同的角色能力
- 需要并行探索多个方向
- 单个 Agent 已经难以兼顾生成、检查、检索与汇总

所以，多智能体不是“更高级的默认架构”，而是一种在问题复杂度上升之后才值得引入的协作结构。

## 1. 生成者-验证者 Generator - Verifier：把“生成”和“检查”拆开

最容易理解的一种结构，是一个负责生成，另一个负责验证。

```text
user -> generator -> verifier -> output
```

### 应用场景
它要解决的问题非常明确：**结果可以先做出来，但不能直接信任，必须经过检查。**

这类模式通常适合下面几种任务：
- 输出存在明确的评判标准
- 一次生成的长尾错误比较多
- 结果需要格式检查、事实检查或规则检查
- 系统更在意可靠性，而不是第一次就生成得多快

尤其适合有一个明确的TODO list的前提下，报告生成后再做结构检查，或者格式要求很严格的结构化输出，以及常见的代码生成后再跑校验。在这个过程中，选择模型也是一门学问，比较常见的是使用Opus写代码，用Codex审查代码，这个角色分工是基于LLM模型的特性完成的。

它的主要优点在于，系统不再依赖同一个 Agent 既负责“写”，又负责“审”。一旦把两个角色拆开，生成器可以专注于产出，验证器则专注于发现问题，很多边缘错误会更容易被拦住。

### 局限性
但它也有清晰边界。Generator - Verifier 的前提，是**系统真的能判断什么叫错**。如果验证标准本身模糊，或者 Verifier 能力不足，那这个结构就会适得其反：看起来多了一层，实际上并没有真正提高质量。对于开放式探索问题，这种模式往往也不够强，因为“好不好”本身就难以稳定定义。

## 2. 调度者-子智能体 Orchestrator - SubAgents：把复杂任务拆给多个执行单元

第二种结构，是一个上层调度者带多个子 Agent：

```text
Orchestrator
  ├── SubAgent 1
  ├── SubAgent 2
  └── SubAgent 3
```

它要解决的问题是：**一个复杂任务无法沿着单一路径顺序完成，必须先拆成多个子任务分别推进。**

### 应用场景
在这种结构里，Orchestrator 负责理解总目标、拆分任务、分配任务，再把各个 SubAgent 的结果汇总起来。它通常适合：
- 复杂 research
- 多章节报告生成
- 多模块代码分析
- 多来源信息汇总
- 需要并行探索多个方向的问题

这一类结构的真正价值，不只是“并行”，而是**把复杂任务拆成多个局部上下文**。每个 SubAgent 在更小、更专注的上下文里工作，往往比一个 Agent 在超长上下文里硬撑更稳定。
与此同时，Orchestrator 作为上层控制点，也让系统具备了更清晰的组织能力：哪些任务可以并行，哪些结果需要合并，哪些方向还要继续搜索。这样可以有效节省主Agent的context空间，主Agent存在时间更长，可以深入处理复杂任务。

### 局限性
但它的问题也同样明显。首先，调度本身就是成本，这种结构通常也意味着更高的 token 消耗与更复杂的调试成本。
其次，SubAgents和Orchestrator需要等待对方响应，才可以运行自己的下一步操作，这本质类似串行运行，没有使用并行提高效率。
最后，在SubAgents和Orchestrator之间进行通讯时，关键的信息可能在传递中被忽视或者压缩丢失。
所以，Orchestrator - Subagents 适合真正需要拆分和并行的复杂任务，但不适合把本来单 Agent 就能完成的任务硬做成“多角色协作”。

## 3. 智能体团队 Agent Team：把协作关系做成长期稳定的小队

和 Orchestrator 不同，Agent Team 更强调稳定分工，而不是一次性调度。

它更像是：有一个协调者维护任务队列，不同 Agent 从队列中领取各自负责的任务。

```text
Coordinator -> Task Queue -> Agent 1 / Agent 2 / ... / Agent n
```
### 应用场景
它要解决的问题是：**任务会持续到来，而且其中有一部分工作值得交给固定角色长期负责。**

这种结构通常适合：
- 任务不是一次性的，而是持续流入的
- 不同类型的问题会反复出现
- 每个 Agent 的职责可以相对固定
- 系统希望沉淀长期的角色分工

它的优势在于稳定。谁负责什么，不需要每次重新决定；某个 Agent 长期负责某类任务，也更容易积累这类任务的经验与惯性，而LLM本身的特性就是偏爱于学习解决问题的具体过程，通过context内部的处理经验，SubAgent在面对同类问题的时候，就可以更快更好地解决问题了。

### 局限性
但 Agent Team 的难点不在“组队”，而在“协作”。如果协调机制不够强，很容易出现几个问题：
1. 子 Agent 彼此看不见对方做了什么、某些任务被重复处理、某些任务积压在队列里，或者局部最优代替了整体最优。也就是说，固定分工虽然稳定，但如果团队之间缺乏有效协同，系统仍然可能退化成多个孤立的小模块。
2. 公共资源是有限的，当面对多个SubAgent处理同一条数据时，可能会产生冲突或者重复修改的问题。

## 4. 消息总线 Message Bus：用发布/订阅取代强耦合调用

第四种结构是消息总线。笔记里总结得很直接：每个 Agent 只做两件事——发布消息，或者订阅消息。

它要解决的问题是：**Agent 之间不想直接互相依赖，而希望通过事件和消息来协作。**

### 应用场景
在这种模式里，Agent 不必知道彼此是谁，只需要知道自己应该发什么消息、监听什么消息。通常系统里还会有一个 Router 或事件分发机制，用来把相关消息路由到合适的 Agent。

这类结构通常适合：
- 事件驱动型任务
- 多个 Agent 需要异步协作
- 模块之间希望保持松耦合
- 任务处理路径不完全固定

它的主要优点是灵活。因为 Agent 之间不再是硬编码调用链，而是围绕消息流协作，所以系统更容易扩展，也更适合异步场景。对于事件密集、流程动态的系统来说，消息总线往往比直接调用关系更自然。

### 局限性
但这种模式的代价，是系统会更依赖可观测性。事件驱动结构一旦出问题，往往不像单点调用那样容易复现，因为错误可能出在某条消息链路、某次路由、某个订阅逻辑里。
其次，Router 的质量尤其关键：如果分发策略不准，系统就会迅速充满噪声、误触发和调试困难。

所以，Message Bus 适合做解耦，却不适合在缺乏日志、追踪与监控的情况下贸然引入。

## 5. 共享状态 Shared State：让多个 Agent 围绕同一份状态持续推进

第五种结构，是多个 Agent 共享同一份持久化状态。

```text
SubAgent <-> Shared State(DB) <-> SubAgent
```
### 应用场景
它要解决的问题是：**多个 Agent 需要围绕同一份中间结果持续协同，而不是依赖一次次显式传话。**

这类结构特别适合：
- deep search
- 多阶段研究与分析
- 基于同一批资料不断补充、修正与迭代
- 多个 Agent 共同维护一个长期工作空间

可以将这种 Multi-Agent 的结构想象成：在一个足够大的房间里，有许多不同领域的专家，他们共同在一块足够大的黑板（相比于context，数据库的容量不可谓不大）面前，各自地从黑板上获取所需的信息，并将处理后的内容写到黑板上。
它的优势在于连续性。一个 Agent 找到的新线索、做出的分析、写下的中间结论，都可以直接进入共享状态，后续 Agent 再基于这份状态继续推进。相比纯消息传递或层层汇总，这种方式更能减少“传话”损耗，也更适合长链路问题。解决问题之后，留下来的数据库中的数据也有一定的价值。

### 局限性
但 Shared State 也是最容易失控的一类结构。因为一旦没有足够强的约束机制，系统就很容易出现并发冲突、状态覆盖、错误传播、流程卡死，甚至僵局。
更重要的是，它会让系统变得更“黑箱”：最后结果虽然形成了，但中间到底是谁改了什么、哪一步开始偏航，往往更难还原。

所以，共享状态很强，但前提是状态设计必须足够清楚，并且配套有版本控制、写入约束、冲突处理和必要的可观测性。

## 这五种结构，本质上对应五类不同的系统瓶颈

如果只背这五个名字，其实意义不大。更有价值的理解方式，是把它们映射回各自对应的系统瓶颈：

- **Generator - Verifier**：瓶颈在输出质量与可检查性
- **Orchestrator - Subagents**：瓶颈在复杂任务拆分与汇总
- **Agent Team**：瓶颈在长期稳定分工
- **Message Bus**：瓶颈在模块解耦与异步协作
- **Shared State**：瓶颈在持续共享上下文与中间状态

从这个角度看，Multi-Agent 的核心不是“多开几个 Agent”，而是**把正确的协作结构放到正确的问题上。**

## 自言自语

我这里只是列举了几个最基本的 Multi-Agent 结构，在实际的使用中，完全可以组合不同的结构形式，生成一个最适合于生产任务的多智能体方案。在不知道怎么选择的前期，可以先找到可以跑通的方法（一般使用调度者-子智能体 或者 生成者-验证者 这两种），再通过运行中暴露出来的问题来进一步优化升级这个结构。

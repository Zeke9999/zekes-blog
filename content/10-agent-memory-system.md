有一部很经典的科幻小说：**仿生人会梦见电子羊吗？** 它常常被理解成一种关于人性、真实与虚假的哲学提问。
在Claude Code源码泄漏事件中，通过拆解分析它的记忆管理系统，最深层的"AutoDream"功能引发了我的关注。在这里，Agent的"做梦"不是一种内心情感世界，而是对记忆的高级管理，这篇笔记是为了拆解这个Agent的六层记忆结构框架。

对于现在的高级Agent来说，如果只把记忆理解成“把历史存下来”，那很容易把问题想浅了，真正困难的从来不是能不能存，而是：

- 什么信息应该被保留
- 什么信息应该被压缩
- 什么信息应该在当前会话中立即生效
- 什么信息应该延迟整理后再进入长期记忆
- 当规则变化时，系统又该如何及时更新运行中的行为


## 记忆系统首先不是一个仓库，而是一套分层上下文系统

这份笔记里反复强调的一点是：记忆不是单点组件，而是分层递进的。

可以把它大致理解为这样一条链路：

- 用户信息
- 持久化规则或长期记忆
- 自动提取后的会话内容
- 必要时再通过外部调用补充信息

真正的重点，不是层数本身，而是：**不同层负责不同时间尺度的信息。**

有些内容需要长期稳定存在，比如规则、偏好、项目约束；有些内容只在当前任务里有用，比如最近的操作过程、当前目标和临时结论；还有一些内容既不值得永久保存，也不应该直接丢掉，而是应该先压缩，再决定是否进入长期记忆。

也就是说，记忆系统真正要解决的，不是“存多少”，而是“在什么时间点，把什么信息放到哪一层”。

Claude Code 这一类系统里的 memory 设计，本质上更像一个 context management system，而不是一个单独的“存档模块”。Claude Code 的记忆系统从浅到深可以分为这六个层级：
1. 指令记忆
2. 短期记忆
3. 工作记忆
4. 长期记忆
5. 摘要记忆
6. AutoDream

## 指令记忆：行为规范与基本信息

第一类记忆，是指令记忆，典型例子是 `CLAUDE.md` 这一类规则文件。

这一层最重要的作用，不是记录发生过什么，而是规定系统**应该怎样行动**。从这个角度看，它其实更接近“运行时规则”，而不是通常意义上的历史记忆。

这类规则还有明显的层级关系，例如：

- 全局
- user
- project
- local

在加载时，会按照重要性从低到高加载，这是因为大模型对新进入的信息更加敏感，如果有冲突的地方，后加载进入的重要信息可以覆盖之前的非重要信息。

这一层还对应一个很重要的区分：有些规则是**始终生效**的，有些则是**行为触发**的。前者更像全局约束，后者更像在特定条件满足后才会被触发，进入上下文。

## 2、短期记忆：对于当前对话的记忆

开启一个新的 Session 之后，本轮对话的内容会生成一个短期的记忆，在这个对话中的所有信息保存在这里。这里有一个层递进的**上下文压缩算法** 共分为4层：
- 微压缩：清除格式或者噪声，只保留语义内容。
- 自动压缩：基于精妙的算法进行压缩。
- 传统压缩：当上下文将要超过限制时进行压缩。
- 摘要压缩：使用类似**摘要记忆**的方法进行压缩，具体可以看**5、摘要记忆（Session Memory）**

## 3、工作记忆：对于工作进度的保留

保留当前的工作进度，确保下次打开这个 Session ，或者打开其他 Session 时，可以从上次的工作断点继续工作。
除此之外，还有我们经常强调的内容，大模型学习处理一种任务最快的方式，就是完全地看到处理任务的整理流程，包括其中的推理步骤以及思考步骤，工作记忆通过保存当前 Session 的成功经验以及失败经验，来形成一套自己的处理流程和方法论，今后面对相同问题的时候就可以处理的又快又好。

## 4、长期记忆：对于 MarkDown 文档文件夹的高效管理

Claude Code 是用 Memdir 系统进行维护和处理的。在管理文件夹中的多个 MarkDown 文档时，长期记忆主要做了两件事：

- 首先是形成目录和索引，具体做法是提取一个文档的主要内容，放到最上面的 30 - 100 行，形成一个索引，当Agent需要读取相关内容时，需要先触发索引，再进行对文档的详细阅读，类似内存分页管理的机制。
- 其次是过滤噪音，对于大模型来讲，它不能很好的地理解"40天前"这样的事件表达，它更偏爱于精确的事件表达，比如"2026年4月14日"，另外，经常发生变化的内容不会用硬编码记录，比如：可以直接从项目代码中分析出来的内容，Agent会有限访问项目代码重新得到，而不是通过记忆存储的方式刻舟求剑。

## 5、摘要记忆（Session Memory）：对话记忆不是简单总结，而是运行时渐进式压缩

如何处理一个 Session 的 Memory ？大部分Agent的处理方法是：在一个 Session 结束之后，将这个对话整体进行一个压缩和总结，但是这往往会**丢失关键信息**。而 Session Memory 处理的不是跨任务长期沉淀，而是**对当前对话过程的临时性维护：** 在Main Agent 在运行时，会额外唤起一个 SubAgent 来同步处理 memory。这个 SubAgent 的工作，不是直接参与主任务决策，而是负责：

- 提炼对话过程中的有效信息
- 更新当前可用的摘要
- 对冗长上下文做 compact

SubAgent 通过同步处理 Memory ，及时更新和复写内容，渐进式生成一份高质量的对话总结，对长途关键信息的保留更好。

## 6、Auto Dream：长期记忆不是实时堆积出来的，而是异步整理出来的

Agent也会做梦？其实只是一种高明的自启动式记忆管理算法。
如果说自动记忆提取是在会话结束后筛选价值，那么 Auto Dream 更像是进一步的异步整理机制。也就是说，系统并不是一有新内容就立刻写死到长期记忆里，而是会在某些条件满足后，再对历史 session 做一次更深入的整合。

Auto Dream 的触发条件大致包括：

- 距离上次交互已经过去一段时间，例如 24 小时
- 两次之间已经累积了足够多的 session，例如 5 个以上

整合的流程，大致可以理解为：

1. 启动探索
2. 收集信息、查看日志
3. 形成轻量笔记
4. 修剪旧记忆，并根据新信息改写

这一步最有价值的地方，在于它不是简单追加，而是**允许旧记忆被修订**。如果再配合锁机制或版本回退能力，系统就不只是“越来越多”，而是“越来越稳”。

这说明一个成熟的记忆系统，并不只是写入机制，还必须有**整理机制、修订机制和回退机制**。




## 注意：为什么记忆系统不要热重载

最后一个非常关键的点，是“为什么记忆系统不支持热重载”。

大部分人的直觉认为，重新载入记忆的方式，在同一个对话中可以产生覆盖旧机制的作用，但是大量的实践证明，LLM在面对前后明显冲突的"记忆"时，会变得混乱且不可预知，因此为了保证质量，重开对话加载记忆，避免热重载是有必要的选择。

## 记忆系统的核心不是容量，而是选择、压缩和时效

最值得留下来的判断不是“记忆有几类”，而是：

> Agent 的记忆系统，本质上不是容量管理，而是上下文选择与时间尺度管理。

很多人谈 memory，容易先想到“多存一点”“长期保留”“跨会话记住更多东西”。但真正做系统时会发现，问题常常恰好相反：不是记不住，而是记得太多、太杂、太旧，太多的噪声导致当前的任务反而失焦。

所以，一个好的记忆系统通常不会追求“最大化保留”，而会更关注：

- 哪些内容应该始终生效
- 哪些内容只属于当前任务
- 哪些内容值得进入长期记忆
- 哪些内容应该延迟整理

也就是说，Agent memory 的真正难点，不在“有没有记忆”，而在于**有没有一套能区分长期、短期、运行时、异步整理和协作共享的机制**。

## 自言自语

目前来讲，AI还没有自己做梦的能力，Auto Dream 只是一种精妙的Agent记忆管理术，通过模仿人类在做梦的行为，来整理记忆。畅想未来，还有什么我们日常中的行为能够给AI的发展提供灵感呢？AI回答中的不可控和混乱是不是一种人类不能理解的正常行为呢？
